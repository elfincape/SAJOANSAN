# 관리허브 권한 정합성 개편

## 목적과 범위

관리자가 직원에게 저장한 권한과 직원의 메뉴·조회·수정·첨부 동작이 일치하도록 한다.
기존 계정, 업무 원본, 변경 이력, 개인 전용 기능, 관리자 전용 설정은 유지한다.
직원별 명시 전체센터 권한이 담당 센터 상한보다 우선하도록 사용자가 확정했다. 현재 변경은 구현·격리 검증 중이며 운영 반영 전이다.

## 확인된 현재 동작

- 권한은 `operations_permissions`의 기본 규칙과 `member_overrides`에 저장된다.
- `operations_permission_for_actor`는 활성 계정과 역할을 검사하고 관리자에게 전체 접근을 허용한다.
- 직원별 `edit/all` 설정도 기사·차량·납품처·코스 등은 센터 소속이 없으면 수정이 거절된다.
- 운영 설정에서 센터가 없는 활성 editor에게 위 자원의 `edit/all`이 저장돼 있으나 최종 edit가 false인 경우를 읽기로 확인했다.
- `operations_can_edit_resource`, 첨부 함수, 일부 API는 권한 함수 이후 역할·센터를 다시 검사한다. 하나만 바꾸면 다른 경로가 계속 거절할 수 있다.
- 기능 카탈로그의 공용 메뉴 범위와 개별 화면의 선택 센터 검사가 다르다. 메뉴의 공용 여부와 실제 자료의 소속 센터는 구분해야 한다.
- 기존 `menu_*` DB 정책은 RESTRICTIVE다. 옛 PERMISSIVE 정책과 함께 있어도 제한 조건을 반드시 만족해야 하므로, 병존만으로 우회 취약점이라고 판단하지 않는다.
- `loadAuthContext(true)`는 이전 요청이 진행 중이면 새 조회 대신 그 요청을 재사용했다. 로그아웃 전에 시작한 응답도 캐시를 다시 채울 수 있었다.

주요 근거: `app/src/lib/auth.ts`, `app/src/lib/permissions.ts`, `app/src/domain/portal-permissions.ts`, `app/src/components/AdminPage.tsx`, `app/src/components/portal/PortalPermissions.tsx`, `supabase/functions/onedrive-auth/handler.js`, `repo-root/sql/operations-member-permissions.sql`, `repo-root/sql/operations-permissions.sql`와 운영 함수·정책의 읽기 조회.

## 확정된 업무 기준

직원별 명시 `수정·전체센터`는 해당 업무의 모든 센터 자료에 적용한다. 담당 센터가 없거나 다른 센터에 소속돼 있어도 이 명시 범위가 우선한다. `담당센터`와 상속된 기본 규칙의 기존 상한은 유지한다. 조회 전용 역할, 비활성 계정, 관리자 전용 기능과 개인 기록의 소유자 제한은 해제하지 않는다.

센터를 자동 배정하거나 기존 직원별 설정을 재저장하지 않는다. 이미 저장된 명시 권한이 정상적으로 작동하도록 권한 함수와 그 소비 경로를 고친다.

## 적용 구조

### 1. 권한 판정의 기준 통합

기존 SQL 권한 함수를 서버 기준으로 유지한다. 사용자 활성 여부, 관리자 전용 여부, 명시 권한/상속, 자료 범위를 한 순서로 판단한다. 직원 역할은 기본 권한과 관리자 기능을 구분하며, 업무별 명시 권한과의 관계를 문서화한다.

동일 업무의 조회·수정·첨부·내려받기에서 별도 역할/센터 검사가 서로 다른 결과를 만들지 않게 정리한다. 기록 소유자와 업무 상태에 따른 실제 제한은 계속 적용한다. 개인 메일과 일일정리의 본인 전용 경계도 유지한다.

### 2. 메뉴와 자료 범위 분리

기능의 공용 메뉴 여부를 자료 접근 범위로 사용하지 않는다. 파일만 처리하는 공용 도구, 센터 데이터 조회/저장 도구, 본인 소유 작업, 관리자 설정을 기존 카탈로그에서 구분한다.

예를 들어 공용 파일 도구는 현재 선택 센터가 바뀌었다는 이유로 기능 권한이 바뀌지 않아야 한다. 반면 도구가 납품처 DB를 조회하거나 센터 자료에 저장할 때는 해당 데이터의 센터 권한을 확인한다. 연결 자료의 열람 권한이 없다는 이유로 전체 화면이 빈 결과를 정상으로 표시하지 않도록 필요한 권한을 설명한다.

### 3. 관리자와 직원 화면에 같은 결과 표시

설정값, 최종 적용값, 적용 범위와 거절 사유를 구별한다. 저장 성공은 요청 성공만이 아니라 저장값 재조회로 확인한다. 사용자 역할/센터·기본 규칙·개별 예외 변경의 버전 및 재시도 이력은 기존 RPC 계약을 재사용한다.

직원 화면은 조회 실패와 빈 데이터를 구별하고, 권한이 거절된 수정 동작을 활성 버튼으로 남기지 않는다. 관리자 계정에서만 검사하지 않고 센터 없는 직원과 타 센터 직원의 결과를 비교한다.

### 4. 권한 갱신과 재시도

이전 권한 요청은 강제 새로고침이나 로그아웃 이후 캐시를 덮어쓸 수 없다. 이 독립 버그의 수정 및 회귀 검사는 이번 브랜치에 포함한다.

열려 있는 페이지의 권한 재확인과 변경 실패 복구는 추가 구현 대상이다. 폼의 입력값을 보존하면서 새 권한을 반영해야 한다. 클라이언트 캐시가 남아도 서버는 매 요청의 실제 권한을 검사해야 한다.

## 검증과 반영 순서

1. 업무 기준을 확정하고 기존 설정으로 변경 전/후 유효 권한 차이를 읽기 산출한다. 의도하지 않은 권한 증가·감소가 없는지 확인한다.
2. 기존 합성 검사에 센터 없음/담당 센터/다른 센터, 상속/명시 거절/조회/수정, 전체/담당 범위, 비활성 계정, 관리자 전용 기능을 추가한다.
3. 격리 Postgres에서 SELECT와 실제 UPDATE/첨부 RPC 결과를 검사한다. 화면 미리보기와 bool 함수만 맞춘 것으로 완료하지 않는다.
4. 일반 직원의 메뉴 진입 → 자료 조회 → 변경 저장 → 재조회, 권한 회수 → 기존 열린 페이지의 변경 거절을 Ego Lite에서 검증한다. 실제 직원 비밀번호나 세션을 추출하지 않는다.
5. 필요한 SQL, API, 화면을 호환되는 순서로 반영하고 운영 설정·원본 업무·이력을 보존한다. 되돌리기는 코드/함수 버전에 한정하며 직원 설정을 임의 초기화하지 않는다.

## 이번 단계의 확인 범위

- 운영 계정의 역할·센터·저장 권한·최종 함수 결과와 관련 RLS 정의를 읽었다. 직원 데이터와 권한은 변경하지 않았다.
- 권한 관련 기존 검사 4개와 추가 auth 회귀 검사를 실행했다. 기존 검사 통과는 전체 구조의 적절함이나 실사용 성공을 뜻하지 않는다.
- 전체 권한 정책 개편, 실제 직원 세션 UI 검증과 운영 권한 변경은 아직 수행하지 않았다.

## 구현된 경계

- 기존 11개 함수의 정확한 이전/수정 후 지문을 확인하는 원자적 교정과 함수 원문 복구 SQL을 준비했다. 새 테이블·계정·권한 행은 만들지 않는다.
- SQL 함수·React/기존 JS 미리보기·포털의 수정 가능 센터·담당자 후보가 명시 범위를 공유한다.
- 첨부는 자원 권한 외에 실제 업로더와 개인 업무 소유자를 계속 확인한다. 저장 완료 뒤의 중복 요청에도 개인 소유자 검사를 건너뛰지 않는다.
- 설정 화면의 범위는 조회와 수정에 함께 적용됨을 표시하고, 개인/관리자 전용 기능의 기존 제약을 설명한다.
- 격리 PGlite에서 실제 업무 생성·수정·완료·재개·재시도·버전 충돌, 첨부 예약·저장·다른 업로더·개인 업무, 담당자 후보, RLS SELECT/UPDATE와 명시 거절, 반복 교정과 알 수 없는 함수 버전의 중단을 확인했다.
