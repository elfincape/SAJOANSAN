# 평택 배차용 구간 조회 및 재사용 설계

## 목적과 범위

평택센터(`002`)의 가배차에 사용할 센터→착지와 착지→착지의 네이버 도로 거리·이동시간을 수집한다. 전체 착지의 모든 조합을 조회하지 않고, 실제 배차에 유용한 후보 구간을 먼저 조회한다. 결과는 센터별로 분리한 DB에 남기고 다음 작업에서 재사용한다.

이 단계는 구간 데이터 준비다. 고정기사 자동 배정, 임시차 섭외, 운행 확정, 전체 배차 최적화는 구현 범위에 포함하지 않는다. 기존 거리·유류비 계산, 코스표, 메일과 브라우저 조회 작업은 유지한다.

## 확인한 기존 구조

- `supabase/functions/naver-distance/handler.js`: 로그인과 센터별 자료 권한을 검사하는 기존 조회 엔드포인트. 결과의 DB 저장은 없다.
- `supabase/functions/naver-distance/provider.js`: 주소 지오코딩과 Directions 호출, 미터·초 단위 구간 결과 및 계산 시각 반환. 현재 좌표 재사용은 한 요청 안에서만 이루어진다.
- `repo-root/js/destination-distance-db.js`: 센터별 납품처 조회와 센터 출발지 정의. 평택의 현재 주소는 경기도 평택시 산단로 263이다. 실제 출입구 좌표는 아직 검증되지 않았다.
- `repo-root/sql/naver-browser-jobs.sql`: 브라우저 거리 조회 전용 작업·재개 테이블. API 구간 캐시나 배차 작업을 이 테이블에 섞지 않는다.
- `tests/charter-fuel-naver.test.mjs`, `tests/destination-distance.test.mjs`: 기존 관련 검사 파일. 검사는 여기에 추가하고 별도의 테스트 파일은 만들지 않는다.

## 확정 업무 조건

- 대림·오양·한성의 이름이 달라도 같은 주소의 실제 업장이면 한 착지다. 고객사별 원본 행과 박스 수는 보존한다.
- 업체명이 같다는 이유만으로 주소가 다른 곳을 합치지 않는다. 같은 좌표만으로 다른 업장을 합치지도 않는다.
- 권역과 도착 OTD가 핵심이다. 한 임시차의 목표는 최대 5개 실제 착지이며, 이를 채우기 위해 먼 곳을 억지로 묶지 않는다.
- 일반적인 소형 후보는 1/2.5/3.5톤이며 큰 물량에는 5톤 후보를 쓸 수 있다. 진입 제한은 별도 제약이다. 일반 Directions 결과가 대형차 진입 가능성을 보증하지 않는다.
- 고정기사의 원래 코스를 우선하는 배차 규칙과 이배송 기본 없음은 다음 가배차 단계에 적용한다. 이 단계에서 운수사·기사·물량을 수정하지 않는다.
- 미래 배차의 OTD는 도착 시각이다. 야적 20분, 대면납 30분, 검수 추가 30분, 센터 준비 60분, 도착 여유 30분은 수정 가능한 시험 기본값이다.
- OTD·메모가 모두 비어 있으면 시간 제약을 임의로 만들지 않는다. 시간 조건이 충돌하면 확인 대상으로 남긴다.

## 대안과 선택

1. 전체 조합 선조회: 비교 데이터는 풍부하지만 500착지에서 센터 구간을 포함해 250,000건이다. 이번 단계에서는 하지 않는다.
2. 필요한 구간만 매번 조회: 시작 비용은 낮지만 반복 작업에서 같은 주소와 구간을 계속 조회한다.
3. 후보 선별 + 영속 캐시 + 누락 구간 추가 조회: 선택한 방식. 초기 후보 데이터로 시작하고 실제 가배차에서 필요해진 구간을 채운다.

## 주소 정리

입력은 평택 납품처 DB 및 사용자가 제공한 파일의 주소 행이다. 원본 파일과 기존 납품처 정보는 덮어쓰지 않는다. 원본 파일명·시트·행·고객사·착지명과 DB 납품처 ID를 해당 주소의 출처로 보존한다.

정규화는 Unicode NFKC, 앞뒤 공백 제거와 연속 공백 정리로 시작한다. 건물번호, 동·호, 출입구 설명을 삭제하지 않는다. 공백을 제외했을 때만 동일한 주소는 지오코딩 결과와 건물번호를 함께 확인해 동일 주소 별칭으로 연결한다. 자동 병합 판단이 불명확하면 확인 목록에 남긴다.

동일한 정리 주소의 중복 입력은 지오코딩 한 번으로 처리한다. 지오코딩 0건·복수 후보·실패는 정상 좌표로 저장하지 않는다. 반환된 표준 주소와 좌표를 보존하되 좌표가 같다는 이유만으로 착지 수를 줄이지 않는다.

한 실제 착지에는 복수 고객사 조건이 붙을 수 있다. 납품 마감·예약 시각이 다르면 모두 보존한다. 같은 주소 이동은 거리·시간 0이고 API 조회는 하지 않지만, 하차·검수 시간은 0으로 만들지 않는다.

## 후보 구간 선정

지오코딩이 확인된 주소를 대상으로 로컬 계산으로 후보를 생성한다. 착지마다 다른 실제 착지 최대 50개를 1차 후보로 둔다. 50은 수정 가능한 조회 범위이지 배송 가능성의 판정 기준이 아니다.

후보 우선순위는 다음 순서다.

1. 기존 자료에서 확인한 실제 연속 배송 구간 또는 실무자가 지정한 구간.
2. 같은 권역과 인접 권역의 가까운 착지. 좌표의 직선거리는 후보 정렬용이며 도로 시간으로 표시하지 않는다.
3. 같은 배송일의 OTD 순서와 서비스 시간을 고려할 때 이어 배송할 가능성이 높은 구간.
4. 권역 밖이라도 남은 후보 중 가까운 착지. 행정 경계가 다르다는 이유만으로 가까운 곳을 배제하지 않는다.

확인되지 않은 OTD나 예상 이동시간으로 후보를 불가능하다고 확정하지 않는다. OTD는 후보 순위의 보조 요소이며, 도로 이동시간을 확보한 후 가배차 단계에서 날짜·대기·서비스 시간과 함께 검증한다. 조회하지 않은 구간은 미조회 상태이지 배송 불가능 상태가 아니다.

방향은 구분한다. A→B와 B→A는 각각 다른 구간이다. 반대 방향을 자동 복사하지 않는다. 예산을 고려해 필요한 방향만 먼저 생성한다.

후보 생성 결과에는 선정 이유·순위·정책 버전을 남긴다. 제외되거나 다음 작업으로 넘어간 구간도 건수로 표시한다. 가배차에서 필요한 구간이 후보 밖이면 같은 예산 정책 아래 단건 추가 조회할 수 있다.

## 조회 예산과 실행

- 첫 수집 작업의 Directions 외부 요청 한도는 센터→착지를 포함해 25,000회다. 착지 수를 500개로 강제 제한하지 않는다.
- 센터→확인된 착지를 먼저 조회하고, 남은 예산으로 후보 간 구간을 여러 출발지에 균형 있게 배분한다. 주소 개수만으로 무료 범위 안이라고 단정하지 않는다.
- 500착지 × 50후보 + 센터 500구간은 25,500구간이다. 전부 캐시 미스라면 최소 500구간은 다음 수집으로 넘어간다.
- 지오코딩은 별도로 최대 2,000 외부 요청을 허용한다. 두 요청 종류의 성공·실패·재시도 건수를 각각 기록한다. 수치는 앱 작업 예산이며 네이버 계정의 월 무료 잔여량을 나타내지 않는다.
- 이미 저장된 주소는 다시 지오코딩하지 않는다. 같은 작업에 저장된 구간은 재개 시 다시 요청하지 않는다. 새 작업에서는 만료 여부에 따라 재조회한다.
- 최초 실연결은 최대 60개 Directions 요청의 시험 작업으로 검증한 후 같은 구현으로 확대한다. 시험 요청도 1차 수집 총예산에 포함한다.
- 공급자에서 실제 사용 중인 상품과 대표 계정·월 잔여량은 아직 미확인이다. 확인 전에는 25,000건 대량 실행을 시작하지 않는다. 일·월 한도 및 초과 사용 설정을 함께 확인한다.
- 한 단건은 경유지 없는 Directions 5 요청이다. 독립 구간들을 하나의 경유 코스로 합쳐 절약하지 않는다. 경유 조건 때문에 독립 단건과 경로가 달라질 수 있다.
- API 옵션은 기존 `RECOMMEND`를 기본으로 사용한다. `MIN_DISTANCE` 기존 기능의 의미나 결과는 바꾸지 않는다. 옵션이 다른 결과는 같은 캐시로 취급하지 않는다.
- 서버 작업은 작은 배치로 실행한다. 기본 외부 동시 요청은 1개, 요청 간격 500ms이며 수정 가능하다. 배치 종료와 성공 구간마다 진행 상태를 저장한다.
- 요청 직전 DB에서 예산을 원자적으로 예약한다. 동시 실행과 재시도도 외부 요청 횟수에 포함해 예산 초과를 막는다.
- 추가 안전장치로 한국 시간 기준 월별 이 수집 기능의 모든 작업을 합산해 센터별 Directions 25,000회, 지오코딩 2,000회로 제한한다. 시험 후 새 작업을 만들어도 예산이 초기화되지 않는다. 이 수치는 네이버 계정의 무료 잔여량이 아니다.
- 인증 실패·한도 응답은 작업을 중지하고 확인 상태로 남긴다. 일시적 통신·서버 오류는 최대 2회 재시도한다. 타임아웃 후 성공 여부를 알 수 없는 요청도 시도 횟수에 포함한다.
- 임대 시간을 둔 작업 잠금으로 중복 실행을 방지한다. 중지 이후 새 요청을 시작하지 않으며, 이미 진행 중인 요청은 완료 또는 중지 상태로 정리한다.

## DB 보존과 권한

기존 납품처·코스·배차 테이블은 원본이다. 다음 세 가지 책임만 새 객체로 분리한다. 기존 테이블에 같은 책임의 구조가 실제로 있는지 구현 직전 다시 확인하고 중복이면 재사용한다.

- 주소 캐시: 센터, 정리 주소, 표준 주소, 좌표, 권역, 확인 상태, 주소 버전, 별칭과 원본 참조, 지오코딩 시각.
- 방향별 구간 캐시: 센터, 출발·도착 주소 ID와 좌표 버전, 공급자, 옵션, 차량 관련 요청 조건, 거리(m), 시간(s), 측정 시각, 갱신 시각. 이 조합에 유일 제약을 둔다.
- API 수집 작업: 실행자·센터·정책 버전, 후보 목록과 상태, 예산과 예약/시도 횟수, 완료·실패·보류 수, 마지막 오류 코드, 잠금 만료, 작업 시각. 배치 단위로 재개할 수 있게 한다.

OTD와 배송일은 구간 캐시 키에 넣지 않는다. 도로 구간 데이터는 재사용하고 업무일의 시간 조건은 가배차에서 적용한다. 반대로 좌표 또는 경로 옵션이 바뀌면 옛 결과를 최신 결과처럼 사용하지 않는다.

API 캐시는 검증된 공급자 응답만 서버에서 쓴다. 브라우저에 네이버 비밀키나 Supabase service role을 노출하지 않는다. 서버가 service role로 쓰더라도 사용자 인증과 센터 권한을 먼저 검사한다. 원본 입력으로 제공된 캐시 결과를 신뢰해 저장하지 않는다.

주소·구간 저장도 서비스 전용 RPC가 현재 작업 잠금과 유효한 임대 시간을 원자적으로 확인한다. 교체되거나 만료된 작업은 캐시와 진행 상태를 덮어쓰지 못한다. 중지된 작업의 이미 진행 중인 응답은 기존 잠금이 유효할 때 저장할 수 있다.

모든 노출 테이블에는 RLS를 적용한다. 주소·구간 읽기는 기존 해당 센터 `delivery_points` 열람 권한을 재사용한다. 수집 시작·재개·중지는 해당 센터 편집 권한이 필요하다. 작업 내용은 실행자 또는 같은 센터의 권한 있는 관리자만 열람한다. 안산 권한만 있는 사용자가 평택 자료를 조회하거나 실행할 수 없어야 한다. 익명 조회·직접 캐시 쓰기는 허용하지 않는다.

## 시간 데이터의 수명

네이버 시간은 조회 시점의 교통 추정치다. 야간 또는 미래 배송 시점의 예측값이나 실제 운행 기록으로 표시하지 않는다. 초기 구간 데이터는 가배차 후보 비교용으로 유지하고 측정 시각을 함께 표시한다.

시간의 신선도 기본값은 30분이며 수정 가능하다. 만료 결과는 오래된 추정치로 표시하고, 가배차 시 실제 선택한 소수 구간만 갱신한다. 25,000구간 전체를 30분마다 갱신하지 않는다. 같은 수집 작업을 재개할 때 TTL 때문에 완료 구간을 다시 전량 조회하지 않는다. 만료된 값만으로 OTD 준수를 확정하지 않는다.

가배차에서 센터 입차 권장 시각을 계산할 때는 모든 착지의 도착 제한, 하차·검수 시간, 도착 여유, 센터 준비 시간을 고려해 역산한다. 자정 전후는 날짜와 한국 시간대를 보존한다. 이 계산 자체는 다음 배차 단계 범위다.

## 기존 화면 통합

오픈소스 전용 메뉴나 별도 도구 페이지를 추가하지 않는다. 평택 관리허브의 기존 납품처/거리 처리 흐름에 후보 미리보기와 수집 상태를 붙인다. 제목·센터 선택·테마·내비게이션은 기존 공통 UI를 따른다.

필수 상태는 전체 원본 주소 수, 실제 통합 착지 수, 확인 필요 주소 수, 생성 후보 수, 캐시 재사용 수, 이번 외부 요청 예상/시도 수, 완료·실패·예산 보류 수다. 조회·중지·재개 버튼과 확인 목록이 있고, 실행 중 반복 클릭은 중복 작업을 만들지 않는다. 무료 잔여량을 모르는 경우 60,000건을 현재 잔여량처럼 표시하지 않는다.

## 검증 기준

- 같은 주소의 여러 고객사 행은 원본을 유지하면서 한 착지와 한 지오코딩으로 처리된다. 이름이 같아도 다른 주소는 유지한다.
- A→B와 B→A, 옵션·좌표 버전이 다른 결과는 분리된다. 같은 주소 구간은 API 호출 없이 0 이동값으로 처리한다.
- 각 착지의 1차 후보는 최대 50개다. 센터 구간·실패·재시도를 포함한 외부 Directions 시도는 작업 예산을 넘지 않는다.
- 500착지의 전부 캐시 미스인 경우 예산 보류가 발생해도 조용히 후보를 누락하지 않는다. 출발지가 많은 경우 일부 출발지만 예산을 독점하지 않는다.
- 작업 중단·재개·중복 실행에서 이미 완료된 구간을 중복 요청하지 않는다. 잠금 만료, 공급자 401/429/5xx, DB 저장 실패를 확인 가능한 상태로 처리한다.
- 지오코딩 복수 후보, OTD 누락·충돌, 자정 전후 조건 때문에 배송 불가능을 임의로 확정하지 않는다.
- 안산/평택 권한 분리, 익명 차단, 캐시 직접 쓰기 차단, 서버 권한 검사와 RLS를 확인한다.
- 기존 네이버 거리·유류비 검사, 관련 UI 검사, lint와 build를 통과한다. 실연결 시험은 성공 시각·거리·시간·저장 결과·재호출 없는 캐시 재사용까지 확인한다.

## 반영 순서

1. 이 설계를 검토한 뒤 구현 계획에서 정확한 파일과 DB 구조를 확정한다.
2. 기존 검사에 회귀·후보·예산·재개 검사를 추가하고, 주소·구간 캐시와 수집 처리 및 기존 UI를 구현한다.
3. 검증한 변경을 기능 브랜치에 커밋한다. 운영 main/Vercel 반영은 해당 커밋의 별도 승인 후 진행한다.
4. 실제 상품·대표 계정·잔여량을 확인한 뒤 60구간 실연결 시험을 한다. 정상 저장과 재사용을 확인하고 남은 1차 예산으로 확대한다.

설계 작성 이후 사용자의 실행 지시와 운영 DB·새 함수 배포 승인을 받아 추가 테이블 3개와 `naver-relations` 함수를 반영했다. 기존 네이버 함수와 main/Vercel은 변경하지 않았다. 실 네이버 시험 조회는 유효한 사용자 로그인 세션이 없어 아직 수행하지 않았다.
