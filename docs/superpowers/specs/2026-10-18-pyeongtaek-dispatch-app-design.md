# 평택 가배차 웹앱 설계서

## 작업 경계

이 문서는 모델 변경 후 구현을 이어가기 위한 설계다. 본격적인 배차 앱 코드는 아직 작성하지 않는다. 사용자 지시에 따라 이 문서를 작성한 뒤 작업을 중단한다.

현재 만들어진 네이버 구간 수집 기능과 앞으로 만들 배차 앱을 구분한다. 구간 캐시 테이블과 Edge Function이 있다는 사실이 실제 구간 데이터 수집 또는 배차 앱 구현 완료를 뜻하지 않는다.

## 목적

CJ 당일 물량표를 받아 평택센터 고정기사에 원래 코스의 물량을 먼저 배정하고, 남은 실제 착지를 현실적인 임시차 코스로 묶는 가배차 도구다. 실무자가 확인·조정하는 초안을 만들며, 차량 섭외·기사 통보·최종 배차 확정을 자동으로 수행하지 않는다.

업무 순서는 물량표 수령, 데이터 확인, 운행 가능 고정기사 확인, 고정차 배정, 임시차 초안 생성, 실무자 조정, 초안 저장·다운로드다.

## 센터와 기존 시스템

- 이안물류의 기존 관리 허브 안에 평택 가배차 기능을 통합한다. 별도 웹사이트나 중복 관리 시스템을 만들지 않는다.
- 센터 코드는 평택 `002`, 안산 `001`이다. 평택 자료만 조회·저장하고 안산 자료와 섞지 않는다.
- 센터 선택, 공통 사이드바, 업무 포털·관리 허브·대시보드 이동, 용어, 현재 CSS와 라이트·다크 테마를 따른다.
- 기존 납품처·코스·기사·차량·운수사·권한 데이터를 재사용한다. 필요한 추가 저장 구조는 구현 시 실제 스키마를 다시 확인한 뒤 최소한으로 정한다.
- 기존 코스표의 OTD 계산이나 기존 배차 기록을 새 도구의 기준으로 일괄 변경하지 않는다.

## 입력과 원본 보존

배차 기준일, 원래 소속 코스, 고객사, 착지명, 주소, 박스 수가 물량표의 핵심 입력이다. 고객사는 대림·오양·한성이며, 한성은 지원 배송이지만 박스 수는 동일하게 기준량을 차감한다.

파일명·시트·행, 원래 값과 정리한 값을 함께 보존한다. 가져오기 화면은 열 매핑과 미리보기를 제공한다. 주소·코스·물량을 불확실하게 추측한 채 자동 배차하지 않는다. 중복 파일이나 동일 행 재가져오기를 식별해 당일 물량이 중복 합산되지 않게 한다.

제공된 배차지시서는 과거 배차 비교 자료다. 이를 앞으로 받을 CJ 당일 물량표와 동일한 형식 또는 운행 완료 증빙으로 단정하지 않는다. 고객사별 원본 행과 물량은 같은 주소를 통합한 뒤에도 유지한다.

박스 수에 소수가 있으면 실제 착지별 물량을 합산한 뒤 반올림하는 것을 기본 처리로 설계한다. 원본 소수는 보존한다. 다른 반올림 단위가 필요해도 원본을 덮어쓰지 않고 설정으로 변경할 수 있게 한다.

## 실제 착지 식별

- 고객사마다 업체명이 달라도 같은 실제 업장·주소이면 한 착지다. 고객사 수만큼 경유지를 늘리지 않는다.
- 업체명만으로 병합하지 않는다. 같은 좌표나 네이버의 같은 표준 주소만으로 서로 다른 창고·동·호·출입구를 병합하지 않는다.
- 공백 차이만 있는 주소는 표준 주소와 좌표가 일치할 때 별칭으로 묶을 수 있다. 그 밖의 주소 차이는 확인 대상으로 남긴다.
- 통합된 착지의 고객사·원래 코스·박스 수·OTD·납품 방식·진입 조건을 모두 유지한다.
- 같은 실제 착지에 원래 코스가 여러 개면 어느 고정차가 가져갈지 확인해야 한다. 통합 때문에 계약 기준량을 이중 부여하거나 서로 다른 고정차로 몰래 분할하지 않는다.
- 같은 실제 착지의 OTD가 충돌하면 임의로 하나를 삭제하지 않는다. 가장 이른 시각으로 일단 덮어쓰기보다는 조건 충돌을 표시한다.

## 고정기사 우선 배정

고정기사는 본인 원래 코스의 물량을 기본으로 가져간다. 물량표의 코스는 원래 소속이고, 초안에서 실제 배송할 차량·기사와 별도로 보존한다.

1톤 100박스, 2.5톤 250박스, 3.5톤 350박스가 확인된 CJ 기준량이다. 이는 실제 적재 중량이나 안전 적재량이 아니다. 5톤 후보를 쓰라는 지시는 확인됐지만 5톤의 CJ 기준 박스 수는 확정되지 않았으므로 500박스라고 자동 가정하지 않는다. 설정·DB에서 기준량이 확인된 차량만 자동 수용량 계산에 사용한다.

착지는 가급적 한 차량이 배송한다. 고정차의 남은 허용량이 23이고 다음 착지가 40이면 23/17로 쪼개지 않고 40박스를 임시차로 보낸다. 고정차의 기준량을 초과할 때도 자동으로 착지 내부의 박스만 잘라내지 않는다. 기존 차로 갈 착지와 임시차로 갈 착지를 나눈다.

고정차에 어느 착지를 남길지는 거리·권역·OTD와 기존 배송 관계를 고려한다. 단순히 물량표 행 순서 또는 박스 수만으로 정하지 않는다. 복수 가능한 안이 있으면 실무자가 선택할 수 있는 초안으로 제시한다.

## 당일 운행 가능 여부

DB의 고정기사 연결을 가져온 뒤 당일 휴무·운행 불가·차량 변경을 확인하는 단계가 필요하다. 당일 변경은 기준정보를 영구 삭제하거나 수정하는 대신 해당 날짜의 배차 조건으로 보존한다.

고정기사·차량·코스 연결이 없거나 운행할 수 없으면 그 물량을 임시차 대상으로 넘긴다. `평택04-2`와 같은 코스는 원래 표기를 보존하고 기본 코스 존재 여부를 조회한다. 표기만 비슷하다는 이유로 같은 차량이라고 간주하거나 수용량을 두 번 부여하지 않는다. 앞선 확인에서 평택04-2와 기본 평택04 변형은 DB에서 발견되지 않았다. 구현 시 최신 DB로 재확인한다.

## 임시차 묶음

일반 임시차는 새 차량을 섭외해 배송하는 개념이다. 초안에서는 섭외 전 차량 규격과 묶음을 제안한다.

- 현실적인 권역과 OTD를 중심으로 묶는다. 차량 수 최소화나 적재율 최대화만을 목표로 삼지 않는다.
- 임시차는 실제 착지 최대 5개를 목표로 한다. 낯선 기사에게 다수 배송을 요청하기 어렵다는 조건을 반영해 5개를 반드시 채우지 않는다.
- 동네 배송의 기본 후보는 1·2.5·3.5톤이다. 물량이 크면 5톤을 후보로 둔다.
- 큰 차가 필요하더라도 납품처의 진입 제한을 무시하지 않는다. 차량 규격과 진입 조건이 충돌하면 실무자 확인 대상으로 남긴다.
- 11톤은 과거 실제 배차에 있지만 이번 초기 자동 추천 범위에는 넣지 않는다.
- 한 착지가 큰 경우 그 착지 전체를 별도 임시차로 빼는 안을 허용한다. 예를 들어 다른 세 착지는 고정차가 처리하고 한 착지 140박스만 임시차로 보낼 수 있다.
- 자동 묶음이 성립하지 않은 착지를 누락하지 않고 미배정 목록에 남긴다.

## 이배송

초기 기본 초안은 이배송 없음이다. 고정기사가 본인 계약량을 초과하거나 인접한 다른 코스를 가져가는 이배송은 부탁·협의가 필요한 별도 선택이다.

초기 버전에서는 실무자가 선택한 경우에만 이배송으로 조정하고, 고정차 기준 초과와 담당자 확인 상태를 명시한다. 이후 버전에서 이배송 없음/포함 대안을 비교할 수 있도록 배정 유형과 원래 코스를 구분해 저장한다. 아직 협의되지 않은 이배송을 확정 배차처럼 표시하지 않는다.

## OTD와 시간 계산

새 배차 도구에서 OTD는 도착 조건이다. 이전·이후·시간 범위·예약 시각을 구분하고 날짜와 한국 시간대를 유지한다. 자정 전후를 단순한 분 숫자 비교로 처리하지 않는다.

OTD와 관련 메모가 모두 없으면 시간 제약이 없는 착지로 배차할 수 있다. 메모에 조건이 있으면 OTD 셀이 비었다는 이유만으로 무시하지 않는다.

시험 기본값은 센터 준비 60분, 야적 20분, 대면납 30분, 검수 추가 30분, 도착 여유 30분이다. 대면납과 검수가 함께 있으면 서비스 시간은 기본 60분이다. 납품처별 DB 값 또는 당일 조정값이 기본값보다 우선하며 초안에는 실제 사용한 값을 보존한다.

이동시간과 앞 착지의 하차·검수·필요한 대기 시간을 다음 착지 도착 계산에 반영한다. 모든 착지의 도착 조건을 만족하도록 역산해 센터 출발 권장 시각을 구하고, 센터 준비 시간을 차감해 최소한 언제까지 센터에 입차해야 하는지 제안한다. 마지막 착지만 기준으로 계산하지 않는다.

이 값은 가배차 추정이다. 조회 시점의 교통 시간을 미래 배송 시점의 보장된 시간이나 실제 운행 결과로 취급하지 않는다.

## 구간 데이터 사용

이미 구현한 `naver_api_addresses`, `naver_api_legs`, `naver_api_jobs`와 `naver-relations` 함수를 활용한다. 센터→착지를 먼저 조회하고, 권역·거리·확인된 배송 관계로 착지별 최대 50개 방향별 후보를 만든다. A→B와 B→A는 다른 구간이다.

최대 50개는 1차 조회 범위이지 배송 가능성의 확정 경계가 아니다. 초안에 필요한 구간이 후보 밖에 있으면 추가 단건 조회·저장으로 보충한다. 직선거리를 도로 이동시간인 것처럼 사용하지 않는다.

시험 60건이 기본이며, 이 수집 기능은 센터별 월 합산 Directions 25,000회·지오코딩 2,000회로 제한한다. 센터 구간·실패·재시도·단건 추가도 포함한다. 이 제한은 네이버 계정의 실제 무료 잔여량이 아니다. 대량 실행 전 상품·대표 계정·잔여량 확인이 남아 있다.

측정 시각을 보존하고 30분을 신선도 시험 기본값으로 둔다. 만료 결과는 오래된 추정치로 표시한다. 전체 후보를 주기적으로 다시 조회하지 않고 실제 초안에 선택한 소수 구간을 갱신한다. 미조회·오래된 구간만으로 OTD 준수를 확정하지 않는다.

현재 수집 실행은 브라우저가 작은 배치를 이어 호출하는 방식이다. 브라우저를 닫으면 현재 배치 이후 호출이 멈추고 저장된 상태로 재개할 수 있다. 무인 장시간 실행이 필요해지면 별도 서버 워커 실행 구조를 설계해야 하며 현재 자동 실행된다고 가정하지 않는다.

## 화면 흐름

하나의 작업 화면에서 다음 단계로 이동한다.

1. 물량표: 기준일과 원본 파일, 열 매핑, 중복·오류·주소 확인 목록.
2. 고정차: 원래 코스, 연결 기사·차량, CJ 기준량, 휴무·운행 불가와 당일 변경.
3. 초안: 고정차와 임시차 배정 목록, 별도의 미배정 목록. 박스 수·실제 착지 수·권역·OTD·차량 제약을 같은 위치에서 비교한다.
4. 상세 조정: 배송 순서, 착지 이동, 차량 규격, 이배송 여부, 서비스 시간·여유 시간 수정과 시간 재계산.
5. 저장·출력: 원본과 초안 버전, 변경 이유, 확인 필요 항목, 다운로드.

자동 초안을 낸 뒤에도 착지 이동·순서 변경·차량 변경을 할 수 있다. 편집하면 해당 구간과 시간 계산을 다시 검증한다. 물량 총합과 모든 원본 행의 배정·미배정 상태를 항상 대조한다. 변경 내용을 저장하거나 버리기 전에는 센터·기준일 전환으로 작업을 조용히 유실하지 않는다.

상태는 진행 중, 초안 생성됨, 확인 필요, 저장됨으로 구분한다. 생성됨이나 저장됨이 실제 섭외·운행 확정을 의미하지 않는다. 기존 업무 UI의 상태 색과 용어를 사용하며 색만으로 경고를 전달하지 않는다.

## 저장과 권한

최소 저장 내용은 센터·기준일, 원본 참조, 초안 버전, 당시 기사·차량·기준량·운행 가능 상태, 실제 착지 묶음과 배정 유형, 배송 순서, 사용한 구간 측정 시각, OTD·서비스 시간·여유 시간, 미배정 사유와 조정 이력이다.

기준정보가 나중에 수정돼도 저장된 과거 초안을 재현할 수 있도록 사용 당시 값을 보존한다. 기사·차량·납품처의 원본 DB를 초안 생성만으로 수정하지 않는다. 기존 배차 DB에 확정 자료를 기록하는 연결은 별도 후속 단계로 둔다.

사용자 인증과 기존 센터별 권한을 적용하고 저장 자료에 RLS를 둔다. 클라이언트가 센터 코드나 소유자를 바꿔 다른 센터 자료를 읽거나 저장할 수 없어야 한다. 서버 캐시 쓰기는 검증된 공급자 응답과 유효한 작업 잠금에 한정한다.

## 구현 순서와 검증

첫 구현 범위는 당일 입력 확인, 고정기사 운행 가능 확인, 고정차 우선 배정, 이배송 없는 임시차 초안, 실무자 조정, 초안 저장·다운로드다. 이배송 시나리오 자동 비교, 11톤 자동 추천, 실제 차량 섭외·통보, 운행 실적 추적은 후속 범위다.

초기에는 검증된 기존 최적화 라이브러리를 검토해 차량 수용량·시간 창·서비스 시간을 처리한다. 고객사 행 전체를 단순 탐욕 순서로 채우는 자체 알고리즘을 곧바로 확정하지 않는다. 고정차 우선·착지 비분할·현장 여유 조건은 선택한 엔진의 입력·제약으로 명확히 표현해야 한다.

필수 검증은 같은 주소의 고객사 통합, 서로 다른 창고 유지, 박스 반올림과 원본 보존, 착지 비분할, 휴무·연결 누락, 기준량 초과, 5착지 제한, 진입 제한, 시간 조건 없음·충돌, 자정 전후, 서비스 시간과 센터 입차 역산, 후보 밖 구간, 오래된 시간값, 전체 물량 대조, 중복 가져오기와 센터 권한 분리다.

과거 배차와 비교할 때는 같은 날짜·원래 코스·실제 주소·고객사 물량을 대조한다. 저장된 일부 임시차 기록을 전체 배차나 OTD 준수 실적이라고 해석하지 않는다. 차이가 있으면 개선으로 단정하지 않고 실무자 판단 근거와 누락 자료를 함께 확인한다.
