# 기존 웹 도구 통합 설계

작성일: 2026-10-16

## 목적과 확인된 환경

배차·기사·차량·업무·첨부파일의 기존 화면 안에서 검색과 처리 확인을 개선한다. 오픈소스 전용 메뉴나 별도 업무 DB는 추가하지 않는다.

- 웹: Vite 다중 HTML 및 Vanilla JavaScript, Supabase 인증/RPC/RLS.
- 검색: `repo-root/js/portal-search.js`의 `operations_search` RPC.
- 업무 이력: `operations-api.js`의 `events()`와 `portal-history.js`.
- 기사 서류: `driver-documents.js`, `driver-document-status.js`.
- 서버: sajo-search, Ubuntu 22.04, x86_64, RAM 957MiB, 디스크 여유 약 4.4GB.
- 로컬 도구: XERJ rc.95, Archify 3.1.0, DevTools MCP 1.10.1, OpenBidKit 2.30.18.

## 1. XERJ: 기존 통합 검색의 문서 본문 검색

기존 업무·기사·차량 등의 RPC 검색을 유지하고 첨부파일 본문 검색을 추가한다. 검색 서버 장애가 기존 검색 전체 실패로 이어지지 않도록 결과와 오류를 별도로 처리한다.

브라우저는 검색 서버의 HTTPS API를 호출한다. API는 사용자 JWT로 기존 Supabase RPC와 RLS를 호출하여 로그인·통합 검색 권한 및 첨부 원본의 읽기 권한을 확인한다. XERJ의 문서 ID 결과를 사용자 JWT로 원본 조회하여 다시 검증한 후에만 제목·본문 발췌를 반환한다. 센터 필터만으로 권한을 대체하지 않는다. 원본이 삭제되거나 권한이 회수된 문서는 반환하지 않는다. 일치 결과를 권한 확인 없이 먼저 발췌하거나 총 건수로 노출하지 않는다.

인덱스는 재생성 가능한 파생 데이터로 취급한다. 원본 DB·OneDrive·파일 저장소를 유지한다. 기존 첨부파일 등록·삭제와 다운로드 경로를 조사하여 동기화 지점을 정한다. 관리자 키를 프론트엔드나 Git에 넣지 않는다.

서버는 XERJ 단일 바이너리와 systemd 서비스를 사용한다. 루프백 바인딩·API 인증을 유지하고 메모리 예산과 색인 동시 실행 수를 제한한다. 처음에는 텍스트 및 텍스트가 포함된 PDF를 대상으로 하고 이미지 OCR·로컬 AI 모델은 실행하지 않는다. 본문 추출이 불가능한 파일도 기존 파일명 검색과 다운로드는 유지한다.

외부 연동은 HTTPS와 사용자 JWT를 사용한다. Let’s Encrypt IP 인증서로 `https://211.233.219.199/search`를 구성하고 하루 두 번 자동 갱신을 확인한다. 인증되지 않은 XERJ 포트는 인터넷에 공개하지 않는다. 원본 로그인·삭제·권한 회수 시나리오가 검증되기 전에는 업무 문서를 일괄 색인하지 않는다.

## 2. Archify: 기존 업무 처리 기록의 흐름도

기존 API로 권한이 확인된 상태·처리 이벤트만 사용한다. 완료·재개·인계 등의 실제 기록을 표시하고 존재하지 않는 승인 단계를 만들지 않는다. 원래 이력 목록과 업무 버튼을 유지하며 같은 상세 영역에서 흐름도를 펼칠 수 있도록 한다.

Archify의 브라우저 실행 계약과 스키마를 조사하여 직접 적용 가능성을 검증한다. 정적 데모를 실제 데이터 연동이라고 표시하지 않는다. 이벤트의 메모와 이름은 안전한 텍스트로 처리하고 다이어그램을 통해 다른 기록을 추가 조회하지 않는다. 런타임을 안전하게 재사용할 수 없는 경우에는 코드 기반 업무 흐름 안내물을 생성해 기존 화면의 도움말에 활용하고 그 적용 범위를 보고한다.

## 3. OpenBidKit: 문서 검토와 재사용 경계

공식 저장소 LICENSE는 AGPL-3.0이다. 앞서 임의의 기능을 간단히 가져올 수 있다고 제안한 내용은 확정 구현 범위가 아니다. 코드를 복사하거나 수정해 웹에 결합하기 전에 해당 배포 방식의 라이선스 조건과 사용자의 수용 여부를 확인한다.

당장 허용된 범위에서는 설치된 원본 데스크톱 앱의 문서 출력이 기존 PDF·이미지 처리 및 서류 등록 화면에서 처리 가능한지 검증한다. 앱의 실제 입력·출력·API 유무를 확인하고 결과를 기록한다. 독립 구현한 누락 검사에 OpenBidKit을 적용했다고 표시하지 않는다. 비공개 웹의 공개 조건을 임의로 바꾸거나 입찰 앱 전체를 1GB 서버에 올리지 않는다.

## 4. DevTools MCP: 기존 화면 개선과 검증

검색·업무 이력·기사 서류·엑셀·PDF 화면을 실제 브라우저로 확인한다. 콘솔 오류, 중복 요청, 대용량 파일 처리와 렌더링 병목 중 확인된 문제만 수정한다. 설치 사실만으로 성능이 개선됐다고 보고하지 않는다. 인증이 필요한 화면을 확인할 수 없는 경우 미검증으로 명시한다.

## 구현 순서와 완료 조건

1. 기존 파일 저장소·권한 및 도구 런타임을 조사하고 실행 계획을 작성한다.
2. 로컬 변경과 검사부터 수행한다. 서버에는 검색 서비스와 제한된 검증 데이터부터 설치한다.
3. 검색·이력의 기존 화면에 통합하고 오류 시 기존 동작이 유지되는지 검사한다.
4. OpenBidKit은 검증된 독립 출력 활용 또는 별도로 승인된 라이선스 범위에서만 통합한다.
5. 기존 검사·빌드와 브라우저 검증을 실행하고 도구별 실제 적용·제약을 보고한다.
6. 현재 작업 폴더의 Git 최상위는 부모 폴더이며 사이트는 미추적 상태이고 원격 저장소가 없다. 기존 연결 저장소를 확인하기 전 전체 사이트를 새 저장소에 임의로 공개하거나 업로드하지 않는다. 올바른 저장소가 확인되면 필요한 변경만 커밋·푸시한다.

서버를 생성했다는 사실만으로 웹 통합 완료를 선언하지 않는다. 전체 통합은 HTTPS 접속·원본 권한 검증·실제 파일 검색·실제 이력 표시 및 배포 확인까지 충족한 뒤 완료로 보고한다.
