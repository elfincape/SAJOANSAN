# 기존 웹 구조 개선 7/7 — 업무·일정·보고 연결

- 저장소: https://github.com/elfincape/SAJOANSAN
- 작업: `/workspace/legacy-workspace-upgrade`, `codex/legacy-workspace-stage7`
- 시작 커밋: `081c3e1e9074f3c90ba8cb46751a8e389b69d4cc`
- [7단계 실행안](../plans/LEGACY-WORKSPACE-UPGRADE.md)의 마지막 단계. 기존 포털 업무/처리 이력과 일별 브리핑을 연결했다. 새 ERP나 새 업무 원장을 만들지 않았다.

## 범위와 실제 발견
기존 업무의 ID·정기 회차·완료/재개·revision 저장 계약은 이미 있다. 처리 이력 API도 당시 `after_value`를 반환하지만 화면은 처리명/일부 메모만 표시했다. 등록 당시 업무 내용이 화면에 나타나지 않는 것을 실제 컴포넌트의 합성 입력으로 먼저 재현했다. 브리핑 조회 클라이언트는 오늘 날짜만 읽고 있었다.

이 단계는 기존 이력·일별 보관본을 읽는 연결을 완성한다. 새 일정 발생기·완료 판정 AI·업무/보고 원장·알림을 도입하지 않는다. 기존 저장/완료/재개 함수를 변경하지 않는다.

## 구현
- 업무 상세의 처리 기록과 기간별 처리 기록에 공통 `PortalEventSnapshot`을 연결했다. 등록 당시 제목·설명·업무 내용, 당시 회차/마감/완료 조건/상태/완료 시각, 당시 양식의 입력과 단계 상태를 표시한다.
- 현재 양식이나 현재 업무 값을 과거 이력에 덧씌우지 않는다. 0·false·빈 문자열을 구분한다. 원래 스냅샷이 없으면 현재값으로 과거를 만들어 내지 않는다.
- 업무 ID 전환 시 이전 이력을 즉시 지우고 조회 중/실패/조회 가능한 기록 없음을 구분한다. 늦은 이전 조회 응답은 반영하지 않는다.
- 브리핑 기준일 선택으로 기존 `operations_ai_results`의 `briefing:YYYY-MM-DD`를 조회한다. 과거 날짜에서는 생성 버튼이 비활성화되고 읽기만 수행한다. 오늘 발송 오류를 과거 보고의 오류로 붙이지 않는다. 잘못된/미래 날짜는 DB 조회 전에 거절한다.
- 보고 기준일·생성 시각·생성 당시 집계와 현재 원본 제목/상태를 구분한다. 보고의 업무 열기는 이름이 아닌 같은 업무 ID로 현재 원본을 조회한다. 접근 거절을 우회하지 않는다.
- 보고 날짜 전환과 원본 열기의 늦은 응답을 무시한다. 조회 실패에 직전 보고를 새 날짜의 자료로 대체하지 않는다. 자료가 없으면 생성하지 않고 없다고 표시한다.
- 오늘 브리핑 생성은 기존 API 그대로이며 업무 저장/완료 함수를 호출하지 않는다. 보고 생성과 업무 완료의 구분을 화면에 표시한다.

## 파일과 재사용 계약
- `app/src/components/portal/PortalEventSnapshot.tsx`: 기존 event.after_value의 읽기 전용 표시.
- `app/src/components/portal/PortalHistory.tsx`: 상세 이력의 스냅샷·조회 상태·업무 전환 처리.
- `app/src/components/portal/PortalHistoryView.tsx`: 기간별 이력에도 같은 스냅샷 표시 재사용.
- `app/src/components/portal/PortalBriefing.tsx`: 날짜별 보관본, 현재 원본과 구분, 늦은 응답 보호.
- `app/src/lib/portal-ai.ts`: 기존 cached()의 기본 오늘 동작을 유지하며 특정 날짜 읽기 추가. 기존 호출자 `Portal.tsx`는 수정하지 않았다.
- 기존 `portalApi.events`, `portalRecord`, `taskPeriod`, `statusLabels`, `MentionText`, 공통 테마·details·날짜 입력을 재사용한다.
- SQL·Edge·RLS·접근 정책·AI 모델/프롬프트·정기 발생 규칙·완료 기준·외부 발송 변경 없음. Supabase 정책 메타데이터 2개 테이블만 읽어 기존 조회 경계를 확인했다. 실제 업무 자료를 읽거나 쓰는 시험은 하지 않았다.

## 확인
내부 Linux Chromium, 실제 React 컴포넌트+합성 세션/API로 14개 확인:
1. 등록 당시 원문 표시.
2. 과거 일별 보고 조회.
3. 과거 조회 시 생성/업무 완료 없음.
4. 월 경계 회차·완료 조건·0/false/빈 값 보존.
5. 완료 근거와 정정/재개 근거 구분.
6. 같은 업무 ID로 현재 업무 열기, 보고 제목과 현재 상태 분리.
7. 현재 업무 변경 후 과거 보고/이력 불변.
8. 늦은 과거 보고 응답이 선택 날짜를 덮지 않음.
9. 과거 보고 조회 실패 시 직전 자료로 대체하지 않음.
10. 보관 자료 없음은 생성으로 대체하지 않음.
11. 이전 보고에서 시작한 늦은 업무 조회가 선택을 바꾸지 않음.
12. 원본 접근 거절 표시, 우회 없음.
13. 오늘 생성 시 업무 완료 상태 변경 없음.
14. 다른 업무 이력 조회 실패 전부터 이전 원문 제거.

실제 `portalBriefing.cached` 클라이언트+Supabase 대역 및 현재 TypeScript 도메인 4개 확인:
- 요청 날짜의 cache_key만 조회, 과거 날짜에 오늘의 발송 오류 미결합.
- 잘못된/존재하지 않는/미래 날짜는 DB 호출 없이 거절.
- 오늘의 발송 상태 조회 유지, 거절 시 오류 전달, 보관 내용 변경 없음.
- 월 경계를 넘는 업무 기간, 완료 후 재개 이력과 같은 업무 ID의 미완료/지연 상태 유지.

## 변경 검토와 한계
직접 변경 검토를 수행했다. 새로운 write 경로가 없고 기존 인증 클라이언트와 RLS를 사용한다. 날짜는 실제 날짜로 검증하고, 과거 조회와 오늘 생성의 경계를 함수/UI 양쪽에서 분리했다. 두 이력 화면이 같은 표시 컴포넌트를 사용한다. 표시 내용으로 완료를 추정하지 않는다.

- 브리핑 보관 단위는 기존의 하루당 최신 캐시 1개다. 같은 날 여러 번 생성한 과거 버전 전체를 새로 보관하는 기능은 추가하지 않았다. 기존 DB에 이미 없는 이전 버전이나 요청 원문을 복원했다고 주장하지 않는다.
- 현재 업무·이력·보고의 읽기 연결이며, 새 정기 업무 생성/업무 완료 또는 운영 데이터 재처리는 수행하지 않았다. 실제 직원 세션·실제 AI 생성/외부 발송은 미검증이다.
- 모든 외부 보고/OneNote·메일 보고서를 통합한 것은 아니다. 해당 기존 경로와 데이터는 유지한다.
- 앞선 단계의 일부 도구만 적용된 버전/재개, 같은 탭 sessionStorage 한계, 실제 OneDrive·AI·지도·Windows 미검증은 유지한다. Notion 폐기 유지.
