## 범위 결정과 기존 기반
기존 파일 저장 전체를 새로 만들지 않고, 공통 업무 첨부와 실제 생성 결과를 쓰는 포털 쿠팡 입문확인 경로에 연결했다. 공통 첨부는 업무·이슈·업무조사가 함께 사용한다. 버전 선택 UI는 쿠팡 결과에 적용되며 다른 도구 전체에 같은 화면을 도입한 것은 아니다.

기존 `operations_files`의 파일 ID·요청 ID·content_hash·첨부 순번·상태·verified_at, OneDrive의 내용 재검증과 덮어쓰기 거절, `operations_task_events.after_value.inputs`의 업무 스냅샷을 재사용한다. 새 파일 저장 제품·원장·SQL 객체·Edge Function·권한 정책을 추가하지 않았다. 과거 업무/파일을 일괄 변환하거나 삭제하지 않았다.

## 구현 결과
- 공통 업로드는 서버가 `saved:true`와 유효한 파일 ID를 반환한 경우에만 완료로 인정한다. HTTP 성공이나 파일 ID만 있는 응답을 DB 저장 완료로 간주하지 않는다. 기존 서버는 바이트 검증과 commit RPC가 끝난 뒤 이 영수증을 반환한다.
- 첨부 목록에 기존 순번·저장 확인 시각을 표시하고, 미완료 행은 `파일 등록 중 · 업무 연결 미완료` 또는 `파일·업무 연결 저장 미완료`로 구분한다. 완료된 파일만 기존 다운로드 경로를 사용한다.
- 다른 업무로 이동하면 선택한 파일·재시도 대상·이전 목록을 분리한다. 이전 업무 요청의 늦은 응답이 새 업무의 선택/목록을 지우거나 덮어쓰지 않도록 기존 generation 검사를 호출 시작 시점에 고정한다.
- 새 쿠팡 생성 결과에 당시 원본 파일 ID, 실행 ID, 생성 요청의 배차 입력, 시작 업무 version, 생성 설정, 결과 연결 계약 버전(`portal-coupang-1`)을 추가한다. 기존 결과 파일 ID 목록·배차 결과·schedule·캡처 범위·입문일·생성시각·이미지 오류는 유지한다. 계약 버전은 새 연결 형식 식별자이며 실제 모델/프롬프트 버전이나 배포 SHA를 증명하지 않는다.
- 파일 보관과 업무의 결과 연결을 구분한다. 일부 파일만 성공하면 성공 개수/전체 개수를 표시하고, 모두 보관됐어도 업무 저장이 실패하면 별도로 알린다. 기존 pending 파일 ID·요청 ID를 재사용해 이미 저장된 파일을 다시 올리지 않는다.
- 생성에 사용한 원본 사진이 현재 업무의 원본과 달라졌으면 결과 연결을 조용히 저장하지 않는다. 선택한 새 사진의 업무 연결이 실패한 경우 이전 원본 ID와 섞어 분석하지 않는다. 이미 보관된 파일은 유지한다.
- `결과 버전·입력 근거`에서 현재 결과와 기존 처리 이력에 남은 과거 결과를 조회한다. 파일 ID 목록이 같은 반복 이력은 한 버전으로 표시한다. 이력은 펼칠 때 기존 API로 읽고 권한을 우회하지 않는다.
- 이전 결과는 당시 파일 ID로 내려받는다. 새 결과는 당시 원본도 같은 ID로 내려받을 수 있다. 구형 기록에 원본 연결이 없으면 기록되지 않았다고 표시한다. 기존 결과 배차정보를 과거의 원 입력이라고 단정하지 않는다.
- 결과 파일 중 일부가 미완료/누락이면 준비된 개수를 표시하면서 확인된 파일의 다운로드는 유지한다. 결과 전체가 준비된 것처럼 조용히 일부만 표시하지 않는다.

## 재현과 검증
수정 전 실제 React 컴포넌트의 합성 브라우저에서 다음 실패를 확인했다: 결과 2개 중 1개가 실패해도 부분 상태가 없었음; `saved:false` 영수증을 공통 upload가 받아들였음; 업무가 바뀌어도 선택 파일이 남았음. 추가 검증 중 업무 연결 재시도 성공 후에도 상태 문구가 저장 중에 머무는 문제를 재현해 성공/변경 안내로 갱신했다. 업무 저장 성공 후 목록 조회만 실패해도 업무 연결 실패로 안내하던 분기도 재현했으며, 저장 확정과 조회 실패를 별도로 표시하도록 수정했다.

내부 Linux Chromium 12사례(주 흐름 11 + 첨부 문맥 1) 통과:
1. 누락/실패 결과 파일의 1/2 준비 표시.
2. DB 미확정 영수증 거절.
3. 부분 결과에서도 준비된 파일 다운로드 유지.
4. 읽기 전용 과거 결과 선택, 현재 원본 ID를 과거 기록에 추정하지 않음.
5. 과거 파일 ID로 다운로드.
6. 일부 결과 업로드 실패 시 미완료 표시와 기존 결과 보존.
7. 파일은 저장됐지만 업무 연결 저장 실패 시 별도 표시.
8. 같은 요청 재시도에서 성공 파일 재업로드 없음, 원본/실행/당시 입력 고정, 그동안 바뀐 입력 보존.
9. 새 결과의 당시 원본 ID 다운로드.
10. 새 사진의 업무 연결이 실패했을 때 이전 원본으로 새 결과 생성 차단.
11. 다른 업무로 이동하면 미업로드 파일 선택이 따라가지 않음.
12. 업무 연결 저장은 완료되고 목록 새로고침만 실패한 경우 저장 실패로 바꾸지 않음.

추가로 도메인 재현에서 과거 스냅샷 불변·중복 이력 수렴·현재 결과 해제 뒤 과거 조회·잘못된 파일 목록 제외를 확인했다. 라이트/다크 화면을 확인했고 새 버전 펼침 제목은 기존 테마 텍스트 토큰을 사용한다.

## 한계와 다음 단계
- 실제 OneDrive 업로드/다운로드, 실제 AI 분석, 실제 직원 로그인 후 저장은 이번에 실행하지 않았다. 브라우저의 세션·파일 API·생성 iframe·업무 저장은 합성 대역이다. 외부 제공자 실증 완료라고 보고하지 않는다.
- 기존 파일은 각 ID가 독립적인 보관본이다. 첨부 순번을 동일 문서의 교체 버전이라고 추정하지 않는다. 결과 버전은 기존 업무 이력의 실제 파일 목록으로 구분한다.
- 완료해 업무 이력에 남은 결과는 새로고침 뒤 읽을 수 있다. 미완료 생성의 File 바이트·pending은 기존 메모리 범위이며 브라우저 종료 후 자동 실행/완전 재개를 추가하지 않았다. 파일 보관 후 업무 연결 전 종료된 건은 기존 첨부 목록에 남을 수 있으나 실행 메타데이터까지 모두 복원됐다고 주장하지 않는다.
- 다른 창에서 원본이 교체돼 결과 연결이 거절된 건은 자동으로 현재 결과로 만들지 않는다. 저장 파일은 남기며 원본/충돌 확인이 필요하다. 이런 실패 지점의 명시적 재개·정리 동작은 다음 6단계에서 실제 경로 기준으로 다룬다.
- 쿠팡의 기존 결과와 일반 업무 첨부를 넘어 거리·용차·기사 서류 등 모든 도구의 버전 UI를 통일하지 않았다. 각 기존 보관 계약은 그대로다. 범용 결과 엔진과 원장 이관은 만들지 않았다.
- Notion 폐기, 기존 외부 제공자/Windows 미확인과 이전 단계 한계는 유지한다. 다음은 6/7단계 실패 후 재개이며 요청 전 시작하지 않는다.
