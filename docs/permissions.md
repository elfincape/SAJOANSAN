# 권한 적용 기준

사용자 속성(활성 상태·역할·담당 센터), 페이지·업무의 열람/수정 조건, 개별 기록의 담당·소유·상태 조건을 순서대로 확인한다. 메뉴와 페이지의 표시만으로 서버 권한을 대신하지 않는다.

| 속성 | 적용 |
| --- | --- |
| 비활성 계정 | 접근 불가 |
| 관리자 | 모든 센터·페이지 접근; 관리자 전용 설정은 일반 사용자에게 부여 불가 |
| 센터 업무 담당 | 페이지 조건을 만족하고 담당 센터에 속할 때 센터 자료 수정 |
| 조회 전용 | 페이지 조건에 따른 열람; 특이사항 처리 상태·본인 알림 확인은 기존 별도 조건 유지 |
| 담당 센터 없음 | 전체 열람 조건은 적용되지만 센터 자료 수정 불가 |

센터 자료 수정의 상한은 tasks/forms/trash/drivers/vehicles/companies/delivery_points/routes/transfers/charter/dispatch_parser/one_top에 적용한다. 로컬 파일 처리 도구의 기존 역할 조건, 담당자·소유자별 기록 검사와 RLS는 유지한다. 임의로 기존 사용자의 역할·센터나 페이지 규칙을 재배정하지 않는다.

‘허용 대상의 담당 센터’는 **사용자를 선택하는 조건**, ‘접근할 자료 범위’는 **접근할 자료를 고르는 조건**이다. 역할 또는 센터 소속이 일치하면 허용 대상이 되며, 수정에는 열람이 포함된다. 전체 사용자/전체 자료를 선택해도 담당 센터 밖 자료의 수정 권한은 생기지 않는다.

기존 사용자 역할·센터는 포털의 **사용자 권한·센터**에서 함께 저장한다. 계정 관리에서는 로그인 아이디·활성 상태와 신규 계정의 초기 역할을 다룬다. 기존 계정 편집은 role 필드를 전송하지 않아 오래된 계정 화면이 최신 권한을 덮어쓰지 않는다. 신규 생성 후 담당 센터 배정은 사용자 권한 화면에서 확인한다.

페이지별 권한과 사용자 권한 화면은 저장 전 미리보기를 제공한다. 미리보기는 페이지 수준의 조건을 설명하며 개별 기록의 담당자·소유자·처리 상태까지 수정 허용을 보증하지 않는다. 실제 접근은 서버의 operations_permission_for_actor와 기존 RLS/API 검사가 결정한다. 권한 변경은 서버의 다음 요청부터 적용되며, 이미 열린 다른 화면은 새로고침 후 메뉴·버튼 표시를 갱신한다.

주요 관리 화면의 수정 폼·버튼은 data-permission-action="edit"를 선언한다. 필요하면 data-permission-resource와 data-permission-center로 자원·센터를 지정한다. 검색·취소·조회 작업과 변경 작업을 구분하며 기존 미지정 화면에는 문구 기반 보조 검사를 유지한다. 프런트 속성은 서버 검사의 대체 수단이 아니다.

센터 URL이 없으면 저장된 선택을 사용하고, 첫 진입에서는 센터를 먼저 선택한 뒤 권한을 확인한다. URL의 명시적 센터가 저장된 선택보다 우선한다.

검증: 로컬 PostgreSQL에서 역할·활성 상태·센터 소속·자료 범위·동작 조합 4,608개를 확인했다. 모의 계정 브라우저에서 미리보기, 관리자 고정, 역할 변경, 사용자 직접 선택, 계정 연결과 조회 전용 제어를 검증했다. 운영 검증은 기존 계정·규칙에 대한 읽기 전용 점검으로 수행하며 임시 계정이나 업무 자료를 만들지 않는다.

대시보드의 course_view는 security_invoker=true로 호출자의 기초 테이블 RLS를 적용하며 익명 열람은 허용하지 않는다. 코스·납품처·기사 등 연결 자료도 각각의 페이지 열람 조건을 따른다.

대시보드 코스는 코스·납품처 열람 권한이 모두 있어야 표시된다. 기사·차량·운수사 열람 권한이 없으면 해당 연결 정보는 표시되지 않는다. 평택 가배차·용차는 charter, 가배차의 상차 기준·착지 관계 설정은 delivery_points, 김해 가배차·배차 요청/회신 초안은 dispatch_parser 권한을 공유한다.
